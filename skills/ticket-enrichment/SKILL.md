# Ticket Enrichment Skill

## Why This Skill Exists

JiraOrchestrator generates tickets from task files. A task file defines WHAT needs to be done. A ticket defines HOW it is communicated to the LLM that will implement it. The gap between the two is enrichment: adding the context, patterns, conventions, and precision that make a task executable without guesswork.

This skill defines:
1. **Minimum thresholds** — the floor below which a ticket fails TicketValidator
2. **Enrichment rules** — what must be added beyond what the task file contains
3. **Pattern library** — fill-in templates for each task type and each section
4. **Anti-patterns** — specific phrases and structures that must never appear

Read this skill in full before generating the first ticket in a batch. The quality of tickets is determined by how well these rules are applied, not just whether all 12 sections are present.

## Section-by-Section Enrichment Rules

---

### Section 1 — Objective

**Minimum threshold:** One sentence. Must describe the post-completion state. Must name the task ID and module.

**Enrichment rule:** The objective must be outcome-oriented, not activity-oriented.

| Activity-oriented (WRONG) | Outcome-oriented (RIGHT) |
|---|---|
| "Implement the AuthService class" | "Implement `AuthService` for MOD-003_authentication (Task TASK-024) so that credential verification and JWT issuance are available to `AuthController` with full bcrypt comparison and refresh token storage." |
| "Create the LoginPage component" | "Implement `LoginPage` for MOD-003_authentication (Task TASK-040) so that unauthenticated users can submit their credentials via a form, receive a JWT on success, and be redirected to `/dashboard`." |
| "Write database migration" | "Create the `refresh_tokens` database migration for MOD-003_authentication (Task TASK-013) so that the table exists with the correct schema before `AuthService` attempts to store refresh tokens." |

**Forbidden words in Section 1:** handle, manage, deal with, appropriate, properly, correctly, relevant, as needed, support, work with

### Section 2 — Context

**Minimum threshold:** All required fields present. `blocked_by` and `blocks` must be exhaustive — every dependency from `task_list.json` must appear.

**Enrichment rule for `blocked_by`:** Do not just list task IDs. Add a brief note on WHY the dependency exists.

```markdown
**This task is blocked by:**
- TASK-009: `users` table migration — AuthService queries this table; it must exist before AuthService can run
- TASK-006: Shared error handler — AuthService uses `AppError` class from the shared error handler
```

**Enrichment rule for `related_modules`:** List every module this task's output will be consumed by.

```markdown
**Related Modules:**
- MOD-004_user_management: imports AuthService.validateToken() for all its protected endpoints
- MOD-006_shopping_cart: uses ProtectedRoute from this module to guard cart pages
```

### Section 3 — Pre-Implementation Checklist

**Minimum threshold:** Architecture review items (minimum 2), dependency verification items (all dependencies from Section 2), existing code review (all files from Section 4), and planning requirement.

**Enrichment rule:** Architecture review items must cite EXACT JSON paths, not section names.

**Wrong:**
```markdown
- [ ] Read security_design.json for the auth design
```

**Right:**
```markdown
- [ ] Read `security_design.json → auth.jwt.payload_schema` and write down the exact fields: confirm it contains `userId`, `email`, and `role`
- [ ] Read `security_design.json → auth.password_hashing.salt_rounds` and note the exact integer value — you will use it in bcrypt.compare()
```

**Enrichment rule for the Planning Requirement:** Be specific about what the plan must contain.

```markdown
**Planning Requirement (mandatory):**
- [ ] Write a step-by-step implementation plan listing:
  1. Every file you will create (in creation order)
  2. Every class/function you will write (with its signature)
  3. The order of implementation (types first, then service, then tests)
  4. Which existing files you will import from (confirm they exist before writing your plan)
- [ ] Identify which error codes from `security_design.json → auth.error_codes` apply to each error condition in AuthService
- [ ] Confirm `JWT_SECRET` environment variable is in `.env.example` (from TASK-002) before writing code that reads it
```

### Section 4 — Existing Implementation State

**Minimum threshold:** If sprint > 1, this section must not be empty. It must list every file, endpoint, table, and pattern that is relevant to the current task.

**Enrichment rule:** Derive this section from `05_context/` files at ticket generation time. Do not invent it. If a file exists in `component_state.json`, include it here with its exact path and what it exports.

**Pattern library — what to include for backend tasks:**

```markdown
**Existing files relevant to this ticket:**
- `src/config/database.ts` — Prisma client instance, exported as `prisma`. Use this in AuthService — do NOT create a new Prisma client. (created by TASK-002)
- `src/shared/errors/app-error.ts` — AppError class. Throw `new AppError(code, message, statusCode)` for all errors. (created by TASK-005)
- `src/shared/utils/logger.ts` — Winston logger. Import as `import logger from '../shared/utils/logger'`. Use `logger.info()`, `logger.error()`, `logger.warn()`. (created by TASK-004)
- `src/shared/validation/validate-request.ts` — `validateRequest(schema)` middleware. Use this in AuthRouter, not inline in controller. (created by TASK-006)

**Existing database tables:**
- `users` — columns: id (uuid), email (varchar unique), password_hash (varchar), role (enum: user|admin|moderator), created_at, updated_at. (migrated by TASK-009)

**Existing environment variables (confirmed in .env.example):**
- `DATABASE_URL` — PostgreSQL connection string (set by TASK-002)
- `JWT_SECRET` — JWT signing key (set by TASK-002)
- `JWT_EXPIRY` — access token expiry (set by TASK-002)

**Existing patterns to follow:**
- Service classes are NOT singletons in this project — they are instantiated in the controller. See `src/example/example.service.ts` for the pattern.
- Error responses use: `{ "error": { "code": "SCREAMING_SNAKE", "message": "human readable" } }`. See AppError class.
- All async service methods return `{ data, error }` tuple. On success: `{ data: <result>, error: null }`. On failure: `{ data: null, error: new AppError(...) }`.
```

**Pattern library — what to include for frontend tasks:**

```markdown
**Existing files relevant to this ticket:**
- `src/api/axios-instance.ts` — Shared axios instance with base URL and interceptors. Import as `import api from '../api/axios-instance'`. Never call `axios.create()` in module-level api files. (created by TASK-015)
- `src/store/index.ts` — Zustand store registry. Import stores from here. Register new store slice here after creating it. (created by TASK-016)
- `src/components/ui/Button.tsx` — Primary button component. Props: `label`, `onClick`, `disabled`, `loading`, `variant: 'primary' | 'secondary' | 'danger'`. (created by TASK-020)
- `src/components/ui/Input.tsx` — Input component. Props: `id`, `label`, `type`, `value`, `onChange`, `error`, `placeholder`. (created by TASK-021)
- `src/components/layouts/AuthLayout.tsx` — Layout wrapper for authentication pages. Centered card layout. (created by TASK-022)
- `src/router/routes.tsx` — Application routes. Add /login route here. (created by TASK-017)

**Existing API endpoints:**
- None yet for auth module (this ticket implements the first auth endpoint call)

**Existing frontend environment variables (in .env and .env.example):**
- `VITE_API_BASE_URL` — backend URL (e.g., http://localhost:3000)

**Existing patterns to follow:**
- API client modules export named async functions, not classes. See `src/api/` for examples if any exist.
- Zustand stores are defined with `create<StoreType>((set, get) => ({...}))`. See `src/store/index.ts` for the pattern.
- Error handling in API client: catch axios errors and rethrow as typed `ApiError` objects with a `code` field matching backend error codes.
- Component files: PascalCase filename matches the default export (`LoginPage.tsx` exports `export default function LoginPage()`).
```

### Section 5 — What to Implement

**Minimum threshold:** Every file that will be created must be explicitly listed with its exact path. Every function/method must have its exact signature. Every API request/response shape must be stated.

**Enrichment rules by task type:**

#### For `service` tasks:
```markdown
**Must implement:**

1. **File: `src/auth/auth.service.ts`**

   **Class: `AuthService`**
   
   Constructor: `constructor(private readonly prisma: PrismaClient, private readonly logger: Logger)`
   
   Method signatures:
   - `async login(email: string, password: string): Promise<LoginResult | AppError>`
     - `LoginResult` type: `{ accessToken: string, refreshToken: string, user: { id: string, email: string, role: UserRole } }`
     - Error conditions:
       - User not found by email → `new AppError('INVALID_CREDENTIALS', 'Invalid email or password', 401)`
       - bcrypt.compare() returns false → `new AppError('INVALID_CREDENTIALS', 'Invalid email or password', 401)`
       - **Note: Both conditions return the same error. Never reveal whether the email exists.**
   
   - `async validateToken(token: string): Promise<TokenPayload | AppError>`
     - `TokenPayload` type: `{ userId: string, email: string, role: UserRole }`
     - Error conditions:
       - Token signature invalid → `new AppError('TOKEN_INVALID', 'Invalid token', 401)`
       - Token expired → `new AppError('TOKEN_EXPIRED', 'Token has expired', 401)`
       - Token missing userId, email, or role fields → `new AppError('TOKEN_MALFORMED', 'Token payload is malformed', 401)`
   
   **Must NOT implement:**
   - Refresh token rotation (TASK-028)
   - Password reset (TASK-030)
   - OAuth integration (TASK-031)
   - Rate limiting (TASK-033)
   - Do not add any HTTP handling (req/res) inside the service — that belongs in AuthController

2. **File: `src/auth/auth.types.ts`**
   - Export `type LoginResult = { ... }` (as defined above)
   - Export `type TokenPayload = { ... }` (as defined above)
   - Export `type AuthError = AppError` (re-export for clarity in consumers)
```

#### For `page_component` tasks:
```markdown
**Must implement:**

1. **File: `src/pages/auth/LoginPage.tsx`**

   **Export:** `export default function LoginPage()`
   
   **Props:** none (page components have no props — they read from the router and the store)
   
   **State management:**
   - Read from authStore: `isLoading`, `authError`
   - Call from authStore: `login(email, password)`
   - Read from router: current location (for post-login redirect)
   
   **Render structure:**
   ```
   <AuthLayout>
     <h1>Sign In</h1>
     <form onSubmit={handleSubmit}>
       <Input id="email" label="Email" type="email" value={email} onChange={setEmail} error={fieldErrors.email} />
       <Input id="password" label="Password" type="password" value={password} onChange={setPassword} />
       {authError && <p className="error-message">{authError.message}</p>}
       <Button label="Sign In" loading={isLoading} disabled={isLoading} variant="primary" />
     </form>
   </AuthLayout>
   ```
   
   **Behavior:**
   - On mount: if `authStore.isAuthenticated` is true, redirect to `/dashboard` immediately
   - On submit: call `authStore.login(email, password)`; on success (authStore.isAuthenticated becomes true), redirect to `location.state?.from ?? '/dashboard'`
   - On error: `authStore.authError` is set by the store; display `authStore.authError.message` inline in the form
   - While loading: disable submit button and show loading spinner inside button
   
   **Must NOT implement:**
   - "Remember me" checkbox (TASK-035)
   - Social login buttons (TASK-031)
   - Password visibility toggle (TASK-036)
   - Registration link styling (link exists but styling is in TASK-043)
```

#### For `state_management` tasks:
```markdown
**Must implement:**

1. **File: `src/store/auth.store.ts`**

   **Store type:**
   ```typescript
   interface AuthStore {
     // State
     accessToken: string | null;
     currentUser: { id: string; email: string; role: UserRole } | null;
     isLoading: boolean;
     authError: { code: string; message: string } | null;
     
     // Actions
     login: (email: string, password: string) => Promise<void>;
     logout: () => Promise<void>;
     setUser: (user: AuthStore['currentUser']) => void;
     clearError: () => void;
     
     // Computed (selectors — Zustand getters)
     isAuthenticated: () => boolean;
   }
   ```
   
   **`login` action implementation notes:**
   - Set `isLoading: true` before calling API
   - Call `authApi.login(email, password)` from `src/api/auth.api.ts`
   - On success: set `accessToken`, `currentUser`, `isLoading: false`, `authError: null`
   - On error: set `authError: { code: error.code, message: error.message }`, `isLoading: false`, do NOT set `accessToken`
   
   **`isAuthenticated` selector:**
   - Returns `true` only if `accessToken !== null`
   - Does NOT check token expiry (token validation is the backend's job)
   - Token storage: `accessToken` is held in memory (Zustand state) only — NOT in localStorage/sessionStorage, per `security_design.json → frontend.token_storage_strategy`
```

#### For `api_client` tasks:
```markdown
**Must implement:**

1. **File: `src/api/auth.api.ts`**

   All functions use the shared axios instance from `src/api/axios-instance.ts`.

   **Functions:**
   ```typescript
   export async function login(email: string, password: string): Promise<LoginApiResponse>
   // POST /api/v1/auth/login
   // Request body: { email, password }
   // Success: 200 { data: { accessToken: string, refreshToken: string } }
   // Error: 401 { error: { code: 'INVALID_CREDENTIALS', message: string } }
   // Throw: ApiError with code from response error.code
   
   export async function logout(accessToken: string): Promise<void>
   // POST /api/v1/auth/logout
   // Request headers: Authorization: Bearer <accessToken>
   // Success: 200 { data: { message: 'Logged out successfully' } }
   // No return value needed
   
   export async function refreshToken(refreshToken: string): Promise<RefreshApiResponse>
   // POST /api/v1/auth/refresh
   // Request body: { refreshToken }
   // Success: 200 { data: { accessToken: string } }
   // Error: 401 { error: { code: 'REFRESH_TOKEN_EXPIRED' | 'REFRESH_TOKEN_INVALID', message: string } }
   ```
   
   **Error handling pattern:**
   ```typescript
   // ApiError type (already exists in src/api/api-error.ts from TASK-015):
   throw new ApiError(response.data.error.code, response.data.error.message, response.status)
   ```
   
   **Must NOT implement:**
   - Token refresh interceptor logic (that belongs in axios-instance.ts, handled in TASK-016)
   - Token storage (that belongs in the auth store, TASK-039)
```

### Section 7 — Technical Specifications

**Minimum threshold:** Technology table with versions, environment variables table, file structure diagram, embedded coding conventions block, git instructions.

**Enrichment rule — conventions block:** Extract relevant conventions from `tech_stack.json` and paste them directly. Never write "follow project conventions."

**Pattern library — conventions block for TypeScript/React/Node project:**

```markdown
**Coding conventions (embedded — do not reference external files):**

**Naming:**
- Files: `kebab-case.ts` / `PascalCase.tsx` for React components
- Classes/Components: `PascalCase`
- Functions/methods/variables: `camelCase`
- Constants: `SCREAMING_SNAKE_CASE`
- Types/Interfaces: `PascalCase` (prefer `type` over `interface` except for class-implementing contracts)
- Enum values: `PascalCase` (e.g., `UserRole.Admin`, not `UserRole.ADMIN`)

**TypeScript:**
- `strict: true` is enabled. All types must be explicit. No implicit `any`.
- `unknown` instead of `any` when type is genuinely unknown — then narrow before use.
- Use `type` keyword for object shapes and unions. Use `interface` only when a class implements it.
- No `as` type assertions unless the comment explains why it is safe.

**Async:**
- All async functions use `async/await`. No `.then()` chains.
- All async functions must have explicit return types: `Promise<T>`, never just inferred.
- Use `try/catch` in controllers and store actions. Services return typed errors, not throw.

**Imports:**
- Order: Node.js builtins → npm packages → local modules (enforced by ESLint `import/order` rule)
- Prefer named exports. Default exports only for React components and Next.js pages.
- No barrel files (no `index.ts` that re-exports everything from a folder).

**React:**
- Functional components only. No class components.
- Props typed inline: `function Button({ label, onClick }: { label: string; onClick: () => void })` for simple components, or extracted to a named type for complex ones.
- No inline styles. Use CSS modules or Tailwind utility classes (per `frontend_design.json → styling_approach`).
- No direct DOM manipulation. Use refs only when necessary.

**Error handling:**
- Backend: throw `AppError`. Never `throw new Error('...')` directly.
- Frontend: store action catches `ApiError`, sets `storeError` state. Never shows raw error to console in production.
- Never use `console.log` in production code. Use the shared logger (backend) or remove before commit (frontend).

**Testing:**
- Every `src/` file has a corresponding test file in the same directory: `auth.service.ts` → `auth.service.test.ts`
- Test file naming: `<filename>.test.ts` or `<filename>.test.tsx`
- No test-specific logic in production code. No `if (process.env.NODE_ENV === 'test')` in src files.
```

**Pattern library — git instructions:**

```markdown
**Git instructions:**

Branch: `feature/TASK-024-auth-service-implementation`
Format: `feature/TASK-<id>-<kebab-summary-max-5-words>`

Commit message format: `TASK-024: <present tense verb phrase>`
Examples:
  `TASK-024: Add AuthService with JWT login and bcrypt verification`
  `TASK-024: Add validateToken method with expiry and payload checks`
  `TASK-024: Add AuthService unit tests with full branch coverage`

Commit granularity: One commit per logical unit (types file, service implementation, tests).
Do not squash into one commit until PR is approved.

PR title: `[TASK-024] Implement AuthService — JWT login and token validation`
PR description must include:
  1. Summary (2-3 sentences: what was built and why)
  2. Files Changed (list with one-line description each)
  3. How to Test (exact commands to run + expected output)
  4. Architecture Compliance (confirm each check in Section 9 was verified)
```

### Section 8 — Success Criteria

**Minimum thresholds by risk level:**

| Risk | Min acceptance scenarios | Min binary checks | Min deliverables |
|---|---|---|---|
| `critical` | 4 G/W/T scenarios | 6 binary checks | exhaustive file list |
| `high` | 3 G/W/T scenarios | 5 binary checks | exhaustive file list |
| `medium` | 2 G/W/T scenarios | 4 binary checks | all created files |
| `low` | 1 G/W/T scenario | 3 binary checks | all created files |

**Enrichment rule — G/W/T scenarios must be self-contained:** They must include the exact setup state (Given), exact action (When), and exact verifiable outcome (Then). No scenario may reference an external test plan.

### Section 9 — Architecture Compliance

**Minimum threshold:** Minimum 3 rows in the compliance table for any ticket. Every row must have a "How to Verify" column that is a specific, runnable action.

**Enrichment rule:** "How to Verify" must be specific enough to execute. Not "review the code" — instead, "decode the JWT from a test login response and confirm the payload contains exactly: `userId`, `email`, `role` — no other fields."

**Pattern library — verifiable compliance checks:**

```markdown
| Check | Architecture Source | Expected Value | How to Verify |
|---|---|---|---|
| Login endpoint path | `api_contracts.json → endpoints[0].path` | `/api/v1/auth/login` | Check `src/auth/auth.router.ts` route definition. Grep: `grep "login" src/auth/auth.router.ts` |
| JWT payload fields | `security_design.json → auth.jwt.payload_schema` | `{ userId, email, role }` | Call login endpoint, decode accessToken with `jwt-decode` or `atob(token.split('.')[1])`, confirm fields match exactly |
| Access token expiry | `security_design.json → auth.jwt.access_token_expiry` | `24h` | Decode JWT, check `exp - iat === 86400` |
| bcrypt salt rounds | `security_design.json → auth.password_hashing.salt_rounds` | `12` | Grep: `grep "saltRounds\|SALT_ROUNDS\|12" src/auth/auth.service.ts` |
| No JWT_SECRET hardcoded | `infra_design.json → environment.required_env_vars.JWT_SECRET` | Must come from env | Grep: `grep -n "jwt_secret\|JWT_SECRET" src/auth/auth.service.ts` — must show `process.env.JWT_SECRET`, not a string literal |
| refresh_tokens table insert | `database_schema.json → tables.refresh_tokens` | all required columns | After login, query: `SELECT * FROM refresh_tokens ORDER BY created_at DESC LIMIT 1` — confirm all 5 columns present |
```

### Section 10 — Risk & Rollback

**Minimum threshold:** Risk level matches what was assigned in the task file. Rollback lists every file created. Database rollback instructions exist if any migration or DB write is involved.

**Enrichment rule — potential failure modes:** List 2–4 specific, realistic failure modes — not generic ones like "bugs." Frame each as: "If X is wrong, then Y breaks."

**Pattern library:**
```markdown
**Potential Failure Modes:**

1. If `JWT_SECRET` is read with a wrong key name (e.g., `process.env.JWT_SECRET_KEY` instead of `process.env.JWT_SECRET`) → tokens signed with `undefined` → all tokens are invalid → login appears to work but every subsequent request fails with TOKEN_INVALID

2. If bcrypt salt rounds are set to a variable instead of a constant (e.g., `parseInt(process.env.SALT_ROUNDS)` without a fallback) → in test environment where SALT_ROUNDS is not set → `NaN` salt rounds → bcrypt crashes → login always returns 500

3. If the refresh token is not stored in the DB before responding → successful login responses are returned but refresh token rotation (TASK-028) cannot validate them → users get logged out unexpectedly after 24h

4. If the JWT payload includes extra user fields beyond `{ userId, email, role }` → token size increases → some clients reject oversized cookies → unpredictable auth failures in browser
```

## Ticket Quality Scoring (Internal Use)

Before submitting to TicketValidator, score the ticket internally:

| Category | Max Points | Scoring |
|---|---|---|
| Section completeness (all 12 present, non-empty) | 20 | 20 if all present, -2 per missing/empty |
| Architecture references (all have exact JSON paths) | 20 | 20 if all exact, -4 per vague reference |
| Acceptance criteria count meets threshold | 15 | 15 if meets/exceeds, 0 if below |
| Acceptance criteria are binary and testable | 15 | -3 per subjective or vague item |
| Coding conventions embedded directly | 10 | 10 if embedded, 0 if referenced externally |
| Verification commands present and runnable | 10 | 10 if present, 0 if absent |
| Context update instructions are exact JSON | 10 | 10 if exact JSON, 0 if vague |

**Minimum score to submit:** 80/100

If a ticket scores below 80, enrich it before submitting. Do not submit low-quality tickets to TicketValidator — they will fail and return with feedback, adding an extra round-trip.
